# Auditoría de rendimiento de Escuela Abierta

Ensayo del 5 de noviembre de 2026. Se usaron builds Next.js de producción, una copia de PostgreSQL 17 y tráfico HTTP en una red Docker privada. No se desplegó ni se escribió en la base del sitio. Ver [mediciones por operación](MEDICIONES.md) y [comandos y reversión](REPRODUCIR.md).

**Resultado principal:** en la contraprueba con 25 clientes durante cinco minutos y doce nombres de búsqueda, la API pasó de **8,75 a 116,93 solicitudes/s**. El p95 de las primeras páginas fue **188–189 ms**, dentro de la meta de 250 ms. Las búsquedas dieron **637 ms** para los nombres variados y **948 ms** para «escuela»: la meta de 500 ms **no se alcanzó** en esa mezcla. La build final respondió 35.160 solicitudes sin errores; la original, 2.649 con 14 errores. Son resultados de este laboratorio, no una capacidad prometida para producción.

## Solicitud y trabajo evitable

La portada renderizada en el servidor llama directamente a handleApi con cinco resultados. La API HTTP usa esa misma función. En el navegador, el explorador omite el fetch inicial si su firma coincide con la respuesta del servidor. Abrir una tarjeta de la lista usa la ficha ya recibida; seleccionar una bandera pide la institución por CUE/anexo. «Asistí acá» sí hace una lectura adicional porque es específica del visitante; su respuesta no se comparte.

Para devolver cinco fichas nacionales en frío, la ruta original transfería a Node 64.495 filas de sedes, otras 64.495 filas agregadas de ofertas (88.490 filas fuente), más el catálogo. Incluso cuando esos grupos estaban en memoria, leía y enviaba un arreglo con los 41.898 CUE con coordenadas activas para calcular la cobertura. En la captura inicial esa última lectura sola tardó 1.273 ms; el agregado de ofertas, 111 ms. No son tiempos de respuesta HTTP. Ver [planes originales](baseline-plans.txt).

Ahora las escrituras manuales preparan las fichas, sus relaciones, los órdenes por nombre y los lotes que ubican a sus miembros. Se usa el mismo normalizador del proyecto. La ruta filtra y pagina en PostgreSQL: se transfieren como máximo cinco fichas en esta vista, un resultado agregado de totales y únicamente las coordenadas de esas fichas. Un listado amplio todavía puede examinar muchas filas en la base para obtener el total exacto. Los índices sirven a la paginación nacional/provincial, la búsqueda parcial por nombre normalizado y la pertenencia de un CUE/anexo. [Planes de la proyección](optimized-plans.txt).

La primera página del país o de cualquiera de las 24 jurisdicciones puede servirse desde un máximo de 25 cuerpos JSON por proceso. Antes de usarla, se lee el padrón publicado y los identificadores de lote activos. Una entrada se genera bajo demanda y los lectores simultáneos comparten la promesa; si falla se descarta. Búsquedas libres, páginas siguientes y asistencia no ocupan esas entradas. La portada y la API pueden reutilizar el cuerpo nacional dentro del mismo proceso. No se añadió Redis. En varias réplicas la preparación ocurre una vez por réplica y versión, no una vez para todo el clúster.

## Método y límites

App: un CPU y 1.500 MiB. PostgreSQL: un CPU y 768 MiB. Pool de la app: tres conexiones, cinco segundos de espera para obtener una, límite SQL de quince segundos. Los clientes envían otra solicitud al terminar la anterior (carga cerrada, sin pausa), con timeout de 30 s. Operaciones rotativas: HTML nacional, API nacional, Tucumán, Buenos Aires, «lorenzo», «escuela», búsqueda vacía de resultados, página 20, ficha por CUE/anexo y puntos de Tucumán. El ensayo de 25 clientes dura cinco minutos de emisión más el drenaje; los demás tramos son sondeos de 20 s, no pruebas prolongadas. Esto no mide usuarios simultáneos reales, Internet, CDN, pintura del mapa ni el proveedor de teselas.

Los errores incluyen timeout, respuesta no exitosa o contenido incorrecto, incluida una portada HTTP 200 con mensaje de error. Los percentiles de la línea base con errores no son latencias de operaciones exitosas; TTFB puede faltar si no llegaron cabeceras. Las mediciones de 1 y 10 clientes de la primera línea base coincidieron con la construcción de la otra imagen. Para comparar servicio bajo carga se prioriza el tramo de cinco minutos. Los tiempos de las sondas tras reiniciar la app son frío de proceso, con la base y el sistema operativo posiblemente calientes. La segunda solicitud repite la misma ruta; se distingue TTFB de descarga completa.

Los límites se aplicaron a los contenedores de servicio; el generador, el host y el proceso de preparación usan recursos aparte. Las muestras de CPU y memoria en [resources.log](resources.log) son instantáneas de docker stats, no un promedio de utilización garantizado. Las fuentes originales permanecen disponibles para revertir; el costo de esta mejora incluye espacio adicional en disco y trabajo durante la publicación manual.

## Mediciones obtenidas

| Operación (25 clientes, 5 min) | p95 original | p95 preparada |
|---|---:|---:|
| Nacional, API | 30.118 ms | 108 ms |
| Tucumán, API | 30.238 ms | 114 ms |
| Buenos Aires, API | 30.191 ms | 118 ms |
| Búsqueda «lorenzo» / «escuela» / sin resultados | 30.025 / 30.027 / 30.031 ms | 365 / 427 / 380 ms |
| Página 20 | 30.019 ms | 390 ms |
| Ficha por CUE/anexo en Tucumán | 30.025 ms | 393 ms |
| Puntos de Tucumán | 30.109 ms | 169 ms |
| Portada HTML completa | 30.585 ms | 263 ms |

En cinco minutos: **428 solicitudes, 302 errores y 1,35 RPS** en el primer ensayo original; **62.987 solicitudes, cero errores y 209,78 RPS** con la preparación. La comparación de los percentiles originales incluye solicitudes que no devolvieron datos. Con la versión preparada, el TTFB p95 de la portada fue 161 ms, frente a 263 ms para descargar el HTML completo. Las metas de 250/500 ms se cumplen para la API en este ensayo; no se alcanzaron 250 ms para descargar todo el HTML. A 50 clientes, el caudal bajó a 196,58 RPS, las primeras páginas llegaron a 288–304 ms y las búsquedas a 811–890 ms, sin errores en la ráfaga de 20 s. El límite está entre las dos cargas ensayadas; no se determinó el punto exacto.

**Frío y caliente sin concurrencia.** Tras reiniciar el proceso, con PostgreSQL ya en uso, la portada original dio 4.310 ms de TTFB y 4.325 ms totales en la primera solicitud; en la segunda, 520 y 608 ms. La preparada dio 1.188 y 1.207 ms en la primera, 44 y 88 ms en la segunda. El primer acceso provincial a Buenos Aires en ese recorrido dio 173 ms y el siguiente 8 ms. Estos valores individuales son sondas, no p95. Los dos primeros arranques del laboratorio fueron mucho más lentos (timeout original; 14,1 s optimizada), por lo que un reinicio, autovacuum o competencia del host no deben presupuestarse como si fueran una lectura caliente. Ver [original](before-probes.jsonl) y [preparada](after-probes.jsonl).

**Qué ganó SQL y qué ganó la caché.** La primera página nacional selecciona cinco filas por índice (0,162 ms para ese SELECT en el plan inicial); todavía hace un conteo exacto si falta la entrada. Con 15 lecturas consecutivas del mismo JSON, el listado preparado **sin caché** dio p50/p95 27,2/66,3 ms; con caché, **2,0/3,4 ms**. No es un promedio bajo tráfico mixto. Las 25 páginas se prepararon en 782 ms y ocupan 204.745 bytes serializadas. El proceso instrumentado pasó de 34,8 MB de heap y 121,5 MB de RSS con dos entradas a 40,7 MB y 133,8 MB con 25 después de las consultas: esos incrementos incluyen asignaciones de solicitudes y memoria aún no recolectada; no son el tamaño retenido exclusivamente por la caché. [Traza SQL y muestras](cache-trace.log).

**Integridad e invalidación.** La comparación completa por jurisdicción verificó objetos de ficha, nombres, orden predeterminado, miembros, ofertas, sectores, sedes y cobertura: 63.822 instituciones, 64.495 miembros y 41.466 instituciones agrupadas con ubicación. Los 41.898 puntos fuente son puntos por CUE, no un conteo de fichas. Las respuestas HTTP se compararon además por provincia, búsqueda con acentos y abreviaturas, membresía, orden por nombre en ambas direcciones y paginación. La prueba de versiones cambió el padrón activo, volvió al anterior, retiró y reactivó el lote; no se sirvieron resultados de la versión anterior. El log SQL registró dos SELECT de fichas para la portada y 50 lectores (25 nacionales y 25 concurrentes de Tucumán). [Paridad completa](full-parity.log), [paridad API](final-parity.log), [caché](cache.log).

**Costo y límite práctico.** La primera preparación sobre el volcado tardó 29 s y la proyección con índices ocupó 143 MB. Una reconstrucción innecesaria de la misma versión elevó la huella física a 225 MB antes de recuperar espacio reutilizable. Por eso las versiones inmutables ya preparadas se reutilizan al volver a publicarlas. La primera matriz mantuvo PostgreSQL y la app cerca de un núcleo cada uno en el tramo sostenido; la app optimizada se observó en torno a 190 MiB. No se agotó su límite de memoria. En ventanas instrumentadas de 10 s, el p95 de adquisición del pool llegó a 1.386 ms en el ensayo original adicional; en ventanas centrales del ensayo optimizado se observaron aproximadamente 73–105 ms. Las sesiones y ventanas difieren: no confundir esos valores con un único p95 global. [Pool original](before-pool.jsonl) y [pool optimizado](after-pool.jsonl).

La búsqueda «escuela» encuentra 25.409 fichas: su conteo exacto y cobertura siguen recorriendo esas coincidencias. El mapa de Tucumán envía 623.514 bytes en la sonda local y su costo de transferencia persiste. Las páginas profundas todavía pagan el OFFSET. Antes de ampliar el pool o contratar infraestructura, medir la proporción real entre búsquedas amplias, descarga de puntos y navegación provincial. Nada de esta prueba mide la capacidad del servidor futuro.

El mapa no cambió su consulta ni su respuesta en este trabajo. En la sonda secuencial su segunda descarga tardó 26 ms original y 81 ms optimizada; el beneficio que aparece en tráfico mixto se explica por menor competencia de las otras rutas, no por un índice nuevo en el mapa. Tampoco se cachea la búsqueda libre: usa PostgreSQL, paginación y conteos del modelo preparado. Para que un proxy no entregue fichas de un padrón ya revertido, la ruta preparada pide revalidación HTTP; el cuerpo compartido se decide después de leer la versión activa.

Host del ensayo: Docker Desktop aarch64, 8 CPU lógicas, 4.109.803.520 bytes de RAM en la máquina virtual. La build original transfirió 2,09 GB de contexto. Se excluyó docs/research del contexto de la imagen: la app no lo lee al servir tráfico y los insumos siguen accesibles para las cargas manuales locales. La última build fue incremental, por lo que su tamaño transferido no es una comparación de imágenes limpias.


## Contraprueba y publicación final

El perfil con doce nombres se ejecutó por separado contra cada imagen, con el mismo precalentamiento de 20 s y sin compilaciones simultáneas. La respuesta nacional pasó de 5.188 a 188 ms de p95; Tucumán de 5.530 a 189 ms; Buenos Aires de 5.075 a 188 ms. El TTFB de portada pasó de 5.616 a 201 ms; la descarga completa de 6.658 a 243 ms. La búsqueda sin resultados pasó de 5.075 a 681 ms y la de nombres variados de 5.004 a 637 ms. Ver [percentiles por operación](MEDICIONES.md) y los registros [original](rotating-before.jsonl) y [final](rotating-final.jsonl). La diferencia con la primera matriz muestra el efecto del perfil, el estado del almacenamiento y la carga del host: no usar sólo la cifra más favorable.

La app original registró un máximo de memoria observado de 450,6 MiB y una mediana de CPU cercana a 100%; la final, 184,6 MiB y 71%. PostgreSQL pasó de 35% a aproximadamente un núcleo completo (medianas de las muestras) y de un máximo de 265,2 a 293,8 MiB. El cuello de botella más probable es el conteo exacto y su cobertura para filtros amplios, que ocupan CPU y conexiones incluso cuando otra búsqueda no encuentra filas. En el plan caliente del primer ensayo el conteo de «escuela» costó 51 ms; en la captura inmediata tras republicar con páginas de disco no calientes llegó a 2.971 ms. No se midió que aumentar el pool ayude. La siguiente comparación útil sería separar los campos necesarios para contar y filtrar de los JSON de las fichas; su efecto aún no está medido.

La matriz original no incluía el CUE sin provincia. Su plan intermedio leía 63.822 fichas para devolver una. Para el CUE/anexo único se retiró el orden nacional innecesario y para el CUE de siete dígitos se consulta el índice de sedes antes de buscar sus miembros. El SELECT exacto final tardó 0,119 ms en la captura posterior a la publicación, frente a 341,55 ms en el intermedio. [Planes tras publicar](published-plans.txt), [paridad del caso exacto](exact-parity.log). El cambio puntual se comprobó en la build final sin extrapolar esa ganancia a los demás endpoints.

En el laboratorio se vació **sólo la proyección de prueba** y se usó el comando real de publicación sobre el padrón existente. Prepararla con un CPU y 768 MiB tardó 15,24 s de vida del contenedor; repetir la publicación reutilizando el corte tardó 3,84 s, incluyendo el arranque del proceso y la copia de scripts. Pico de memoria del cgroup observado: 230.449.152 bytes (220 MiB). La proyección preparada ocupó 143 MB, con 63.822 fichas, 64.495 miembros y paridad completa. Los índices GIN se limpian de inserciones pendientes y se actualizan sus estadísticas antes de terminar la primera publicación. [Tiempos](preparation-events.log), [memoria](preparation-memory-bytes.log), [paridad después de publicar](published-parity.log).

Preparar las 25 respuestas tardó 0,78 s con lecturas calientes y 6,08 s en la prueba posterior a la republicación; en ambas ocuparon 204.745 bytes serializadas. Se comprobó también que dos visitantes reciben cookies diferentes y respuestas de asistencia privadas, y que el listado público no emite Set-Cookie. [Prueba final de versiones](final-cache.log) y [aislamiento de cookies](cookies.log). Los servicios de prueba se detuvieron; se conservaron los artefactos e imágenes locales y no se desplegó nada.
